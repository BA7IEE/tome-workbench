# 单件误确认组合纠错 · rc.14

PR #58 的普通 UX 和 #59 的只读核对是各自已验证的固定候选。本增量基于 #59，在独立后续分支实施；它们的绿色结果不验证本增量。生产记录未改动。

只读 `confirmation-correction-preview` 继续返回 REVIEW_ONLY/不授权写入。新增 `confirmation-compensation-preview` 和 `revoke-confirmation`，以及按纠错 ID 的 `restore-preview` / `restore`，只供管理员。表单显示来源、名称、完整 TM，要求三字原因与显式确认；请求必须携带候选、商品、采购行当前版本和只读核对摘要。

撤销只接受唯一原新建确认 Receipt、单一候选/主来源/ACQUISITION 链、匹配采购行、BUSINESS 首周期 AVAILABLE 或 PAUSED；已关联/复用、共享 TM、成本/成交/预留/观察/询盘/移动/报价/任务/发布/资料包/导出/渠道/选品及整单财务、退货依赖均阻断。所有历史依赖都计入，即使已取消或作废。

一次事务将 Item 软删除为 PAUSED/待审核，候选 EXCLUDED，关联采购行 EXCLUDE，保存前后快照、新版本修订、Audit、Outbox、Receipt 和专用纠错历史。实物在手、原始确认时间、原号、原文件及 Source/采购关联不改；绝不删除原确认回执或腾出编号。

专用组合恢复验证活动纠错状态与锚点、唯一原确认回执和所有当前依赖，恢复原 Item、候选 CONFIRMED、采购行 INCLUDE，保持 PAUSED/待审核。它不重新发布、重启任务、重分摊或反改任何成本。撤销后其他正确商品仍可录入订单依据；若形成新的整单财务事实，原件恢复须保留状态并交管理员核对。

Commands 先取得 financial-journal，再校验当前角色/Session 和原请求 Receipt。纠错命令尝试取得候选、Item、Source/sourceKey、采购行、经营采购订单和导入订单锁，资源忙时失败而不排队形成反序死锁。锁后重新读取和核对全部版本、归属及依赖。数据库活动唯一索引、不可覆盖历史、延迟组合约束、引用资源锁和提交时检查为第二层保护；普通商品、候选、采购恢复与成本写入另有明确领域拦截。

账号隔离的 IndexedDB 在 POST 前保存原路径、载荷和请求号。存储失败不提交；未知结果和登录失效保留，跨窗口恢复原内容和键来核对回执。已撤销卡片仍有核对撤销回执入口；后续恢复和撤销共用同一候选恢复槽，必须先核对原未知提交。明确 400/409 拒绝保留原因，关闭后重新核对新版本，不能自动采纳最新版本。

新增 forward migration `202610120021_confirmation_compensation` 不转换现有记录。旧迁移字节和封印保持不变。升级需停写、原版本一致性备份清单、固定新源码正式迁移与统一启动；这里不执行生产迁移。

验收采用原完整 CI：真实 PostgreSQL/HTTP、双浏览器相同范围，包含原真实写入后丢回执、并发、HA、全模型恢复、审计与打包。新增具体覆盖见 AC_MATRIX。最终通过数和指纹应取本增量固定 head 的实际日志；本地仅轻量 lint、语法和无连接的 schema 校验，未重构建或启动数据库/浏览器。真机手指/键盘 UAT 和精确生产后端 SHA 仍未取得。
