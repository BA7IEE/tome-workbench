# rc.13 继续排查记录

本轮发现并修复「原请求写入成功但回执丢失，随后重试时登录失效」的组合故障。

- 通用表单及WriteAttempt原来会用后续401覆盖未知结果标记，改名后可能生成新命令，重复创建商品或询盘。改为保持未知状态，直到核对原请求成功。
- 完整录货和图片弹窗同样会在后续登录拒绝后重置上传键与载荷。改为保留原文件、原来源与请求号，登录恢复后继续原上传。
- 完整录货上传原先吞掉认证错误，只显示通用上传失败，无法原位登录；现在传递认证错误给编辑器。图片弹窗补充同账号恢复登录入口，保留队列。

修复前两项浏览器用例明确失败，修复后复核真实写入数量及请求号。图片测试还核对1500像素宽合成原图的SHA256及原来源。定向测试中纠正了一个过早结束断言：原「已保存」也会匹配「已保存0/1」，现在必须等待「已保存1/1」，没有放宽成功条件。保留首次明确拒绝后修改来源再上传的既有行为。

未修改服务端鉴权、库存、账务、媒体授权、冻结快照或数据库结构。测试写入仅在tome_test。完整结果见本版validation报告；不等于真实对客发布验收。

首次完整运行中WebKit两条上传用例失败，诊断确认route.fetch只暴露647字节字段而缺失图片二进制。上传故障注入改为实际XHR原样到达服务端并取得真实成功响应后，丢弃首次成功回调并触发原错误处理；核对真实文件SHA256、来源、数量和同一请求号。没有更换图片、伪造服务端成功或跳过WebKit用例。修正后五项定向WebKit用例通过，重新执行整套验证。
